# schrt.ru

Простая платформа для преподавателей и студентов: создание заданий, приём файлов, управление группами и AI-проверка сданных работ.

## Возможности

### Для преподавателя

- Создание групп; список студентов можно загружать из CSV, а можно не загружать — он пополняется сам из сдач.
- Пометка «из сдачи» у студентов, которых группа набрала сама, фильтр «Кто в списке» и удаление такой записи одной кнопкой.
- Сортировка групп (по названию, числу студентов, числу заданий, дате) и поиск по названию.
- Сортировка заданий по группам, названию, дедлайну и дате создания + фильтр по группе.
- Создание заданий с дедлайном и опциональным **жёстким дедлайном**.
- Автоматическая генерация короткой ссылки на задание (`4 символа [a-z0-9]`).
- Просмотр сданных работ, скачивание отдельных файлов или всех сразу в ZIP.
- Сортировка студентов и сданных работ по фамилии, сдачи, среднему баллу, времени и оценке.
- Экспорт отчёта по группе в XLSX: лист «Сдачи» и лист «Оценки» (оценки по всем заданиям, средний балл).
- Экспорт оценок всей группы в CSV — одна таблица «студент × задание».
- AI-проверка сданных работ с оценкой по шкале 2–5 и развёрнутым комментарием.
- Ручной запуск AI-проверки со страницы задания: для всех работ сразу или для одной конкретной.
- Дашборд **«AI-проверка»** (`/grading`): видно все непроверенные работы по всем группам, причину (нет ключа, нет текста задания, ошибка модели, зависело в очереди), распределение оценок и работы на 2–3 для ручного просмотра.
- Быстрое добавление текста задания прямо из дашборда — непроверенные работы этого задания сразу уходят в очередь.
- Экспорт AI-оценок по заданию в CSV (плюс колонки «Попыток AI», «Время проверки», «Ошибка AI»).

### Для студента

- Переход по короткой ссылке `/s/xxxx`.
- Выбор студента из списка группы — имя и фамилия больше не вводятся в одном поле.
- **Отдельный файл от каждого студента**: если работу делали вместе, каждый участник добавляется отдельной строкой со своим файлом.
- Если студента нет в списке группы, он вписывает имя и фамилию и **добавляется в список автоматически**.
- Загрузка файла перетаскиванием или через диалог выбора, проверка размера и формата до отправки.
- Возможность групповой сдачи (если разрешено в задании) — не более одного файла на человека.

### Оформление

- Светлая, тёмная и системная темы: переключатель в шапке, выбор запоминается в `localStorage`, тема применяется до отрисовки интерфейса.

## Быстрый старт

Требования: установленные [Docker](https://docs.docker.com/get-docker/) и [Docker Compose](https://docs.docker.com/compose/install/).

```bash
# 1. Клонировать репозиторий
git clone https://github.com/rvnzz/schrt.git
cd schrt

# 2. Подготовить конфигурацию
cp .env.example .env

# 3. Запустить все сервисы
#    app      — FastAPI + собранный frontend
#    postgres — база данных
#    minio    — S3-хранилище файлов
#    ai-grader — фоновый воркер AI-проверки
docker compose up --build
```

После запуска:

- Приложение: http://localhost:8000
- REST API: http://localhost:8000/api
- MinIO Console: http://localhost:9001

Дефолтный преподаватель:

- Логин: `teacher`
- Пароль: `teacher`

> Порт приложения настраивается переменной `APP_PORT` в `.env` (по умолчанию `8000`).

## Production

Для production используется готовый образ из GitHub Container Registry.

```bash
cp .env.example .env
# Обязательно измените SECRET_KEY и FIRST_TEACHER_PASSWORD
# Добавьте OPENCODE_GO_API_KEY, если нужна AI-проверка

docker compose -f docker-compose.prod.yml up -d
```

По умолчанию скачивается образ `ghcr.io/rvnzz/schrt:main`. Чтобы использовать другой тег, задайте переменную `APP_IMAGE`:

```env
APP_IMAGE=ghcr.io/rvnzz/schrt:v1.0.0
```

### Важные production-настройки

- `SECRET_KEY` — смените на длинный случайный ключ.
- `FIRST_TEACHER_PASSWORD` — задайте надёжный пароль для первого преподавателя.
- `OPENCODE_GO_API_KEY` — добавьте ключ для включения AI-проверки.
- `LINK_PREFIX` — укажите публичный URL вашего приложения, например `https://schrt.example.com/s/`.

## AI-проверка работ

AI-проверка реализована через официальный API **opencode-go** (модель `glm-5.3-flash` по умолчанию).

### Как включить

Добавьте в `.env`:

```env
OPENCODE_GO_API_KEY=your_api_key
OPENCODE_GO_BASE_URL=https://opencode.ai/zen/go/v1
OPENCODE_GO_MODEL=glm-5.3-flash
WORKER_POLL_SECONDS=5
```

Без ключа воркер запускается, но проверка не выполняется — у сдачей будет статус `disabled`.

### Как это работает

1. Преподаватель в форме задания заполняет поле **«Текст задания для AI (markdown)»**. Этот текст видит только AI-агент.
2. После загрузки файла студентом фоновый воркер `ai-grader` извлекает:
   - текст из `txt`, `md`, `pdf`, `docx`, `xlsx`;
   - изображения из `docx`, `pdf` и графических файлов.
3. Агент получает задание, текст работы и изображения, затем возвращает оценку по шкале **2–5** и развёрнутый комментарий.
4. Результат отображается в таблице сданных работ. Длинный комментарий свёрнут по умолчанию и разворачивается по клику.
5. Преподаватель может вручную запустить повторную проверку:
   - **«Проверить все работы AI»** — для всех сдач со статусом `disabled` или `error`;
   - **«Перепроверить»** — для одной конкретной сдачи.
6. Есть экспорт всех AI-оценок по заданию в CSV (кнопка **«Экспорт оценок AI (CSV)»**).

### Дашборд AI-проверки (`/grading`)

Страница собирает состояние проверки по всем группам преподавателя: четыре карточки
(проверено, в очереди, ошибки, без текста задания) кликом фильтрают таблицу, далее —
фильтры по группе и виду проблемы, поиск по группе/заданию/студенту/файлу и сортировка
колонок. Каждая строка объясняет, почему работа не проверилась:

| Вид | Что значит | Что делает дашборд |
|-----|------------|--------------------|
| `error` | запрос к модели упал или ответ не разобрался | кнопка «Перепроверить», показывает текст ошибки и число попыток |
| `no_brief` | у задания нет текста для AI | кнопка «Добавить текст задания» |
| `not_queued` | текст задания появился уже после сдачи | кнопка «В очередь» |
| `stale_pending` | работа ждёт дольше `stale_minutes` (по умолчанию 15) | подсказка: проверьте контейнер `ai-grader` |
| `ai_off` | не задан `OPENCODE_GO_API_KEY` | баннер с объяснением |

Диалог текста задания сохраняется через `PATCH /api/assignments/{id}` и сразу вызывает
`POST /api/ai/enqueue` — непроверенные работы этого задания уходят в очередь без
дополнительных кликов (работы без текста эндпоинт пропускает и возвращает счётчик
`skipped_no_brief`). Ниже таблицы — распределение оценок 2–5 по заданиям и список работ,
оценённых на 2–3, которые стоит пересмотреть человеком. Пока в очереди есть работы,
страница обновляется сама каждые 10 секунд.

Данные отдаёт `GET /api/ai/overview` (параметры `group_id`, `kind`, `stale_minutes`,
`problem_limit`), массовые действия — `POST /api/ai/enqueue` с одним из селекторов
`assignment_id`, `submission_ids`, `scope: "all_errors"` и лимитом до 500 работ за вызов.

Диагностика хранится в отдельных колонках `submissions`: `ai_error` (причина отказа —
больше не затирает комментарий модели), `ai_attempts` (число попыток) и `ai_checked_at`
(время последней проверки). Миграция `d5a83c1e7b40` переносит текст аварии из `ai_feedback`
в `ai_error` у существующих строк со статусом `error`.

## Сдача работ и экспорт оценок

### Как сдаёт студент

Страница `/s/{code}` принимает **по одному файлу от каждого студента**. Участник выбирается из
списка группы (поиск по фамилии или имени), а не вписывается в поле с именем — так работа
гарантированно привязывается к нужному студенту в отчётах преподавателя. Если работу делали
вместе, включается режим «Делали работу вместе»: каждый участник добавляется отдельной строкой
со своим файлом, и сервер создаёт отдельную сдачу на каждого.

#### Автопополнение списка группы

Если имени студента нет в списке группы, он вводит имя и фамилию вручную — и сервер создаёт
запись в `students` с флагом `is_auto_added = true`, а сдачу привязывает к ней. Так список
группы собирается сам из реальных сдач, а работы не остаются «висящими» без студента.
Повторная сдака тем же именем существующего студента дубликат не создаёт: сравнение идёт без
учёта регистра. В интерфейсе группы такие записи помечены бейджем «из сдачи», их можно
отфильтровать («Кто в списке»: все / из CSV / из сдач) и удалить.

Флаг добавляется миграцией `9d1e4b7a2c53_auto_added_students.py` — после обновления образа
выполните `alembic upgrade head` (в Docker это делает `entrypoint.sh` при старте).

Формат запроса `POST /api/submit/{code}` (`multipart/form-data`):

| Поле | Описание |
|------|----------|
| `participants` | JSON-массив `[{"first_name": "Иван", "last_name": "Петров"}, ...]` |
| `files` | по одному файлу на каждого участника, в том же порядке |
| `is_group_work` | `true`, если работу сдавали вместе |
| `first_name`, `last_name` | имя основного сдающего — для обратной совместимости со старыми клиентами |

Сервер отвечает `400`, если файлов меньше или больше участников, если один студент добавлен
дважды или если несколько файлов пришли без группового режима. Старый формат (один `file` +
`group_members`) по-прежнему принимается.

Ответ: `{"success": true, "count": 3, "submitted_at": "...", "is_late": false, "auto_added": ["Иванов Пётр"]}` —
в `auto_added` фамилии студентов, которых группа набрала при этой сдаче.

### Экспорт оценок группы

Со страницы группы (`/groups/{id}`) доступны две кнопки:

- **«Оценки группы (CSV)»** — `GET /api/submissions/groups/{id}/grades-csv`, таблица
  «студент × задание» со средним баллом и числом заданий без оценки.
- **«Отчёт группы (XLSX)»** — `GET /api/submissions/groups/{id}/report`, два листа: «Сдачи»
  (✅ вовремя, ⚠️ просрочено, ❌ нет работы) и «Оценки» (оценки AI по каждому заданию).

Оба запроса выполняются с JWT-токеном из интерфейса, поэтому файлы скачиваются без отдельного
входа в API. Оценки по конкретному заданию по-прежнему выгружаются со страницы задания
(`GET /api/assignments/{id}/grades-csv`).

## CI/CD

В `.github/workflows/build.yml` настроен GitHub Actions workflow, который:

- запускается при пуше в `main`/`master` и при создании тегов `v*`;
- собирает production Docker-образ;
- публикует его в **GitHub Container Registry**: `ghcr.io/rvnzz/schrt`.

> Сборка выполняется только для платформы `linux/amd64`.

## Архитектура

Приложение собирается в **один production Docker-образ**:

1. **Frontend-builder stage** — собирает Vue-приложение (`npm run build`).
2. **Backend stage** — копирует Python-зависимости и код FastAPI.
3. **Final stage** — объединяет backend и статику frontend в одном контейнере.

FastAPI раздаёт собранную статику по корневому URL, а API доступно по префиксу `/api`. Это позволяет развёртывать приложение как единый сервис без отдельного nginx для фронтенда.

Отдельный контейнер `ai-grader` использует тот же образ, но запускает фоновый воркер (`python -m app.worker`), который асинхронно проверяет сдачи из очереди в PostgreSQL.
